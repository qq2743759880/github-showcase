# 项目主介绍

> 本文是 github-project-showcase 的公开投影（F02 产物），事实全部来自 [docs/verification/verification-results.md](verification/verification-results.md) 所引的落盘证据；对外一律称「项目维护者」。

## 它是什么

github-project-showcase 是一个面向 Agent 的 GitHub 项目展示编排 Skill。它把「给项目做一个像样的 GitHub 门面」从一篇文章的写作，变成一条可验证的工程链：读取项目契约、路由十个 phase 槽位、调度 20 件固定版本的子能力实体、逐产物验收、范围审查、本地打包，最后由四道质量门机检把关。

## 解决什么问题

项目展示常见的失败不是「写得不好」，而是「不可信」：数字没有出处、图画了不存在的关系、该公开的没讲清、不该公开的泄漏了、README 里的命令 clone 下来跑不通。普通 README 生成器无法回答这些问题，因为它们不做取证、不做验收、不做范围审查。本方法把这三件事做成硬性阶段，并把验收标准写进契约：验不过等于不产出。

## 输入什么

用户准备三样东西，全部写进一份 adapter 契约文件：

1. **项目目录**——只读取证范围（代码、文档、知识库、设计稿皆可）；
2. **项目事实**——预核事实文件；没有就由 F01 取证现场回填；
3. **公开范围**——发布授权状态、导出布局、审查轴。

契约里没填的字段按「无数据」处理并如实声明，禁止编造。

## 最后得到什么

一个本地展示成品包：

- README（第一屏只讲用户价值与输入输出）；
- 架构图与流程图（可编辑图源 + 渲染成品 + 逐节点事实映射 + 「不存在的边」声明）；
- 能力/规模图表（只用有证据的数字；无指标则不产数据图）；
- 首屏视觉（Hero 卡，真实渲染验收）；
- 安全与范围审查记录（凭据扫描、隐私、许可、授权四轴）；
- 资产消费台账与验证结果存档；
- 代码项目额外要求：源码随包，并在全新 clone 上跑通「装依赖 → 启动检查 → 装验证依赖 → 测试」全链，实测输出写进 trace。

发布授权未批准时，全程零远程写入，止步 READY_FOR_APPROVAL——「可发布」与「已发布」被契约明确区分。

## 与普通 README 生成器的区别

生成器替你写文章；本方法替你把关。区别落在四件可复核的事上：事实纪律（每个数字有 evidence 与 as_of）、能力分工（十槽位各有调用形态与 successCheck）、质量门（资产消费 / 读者理解 / 表层分 / 自展示，全部机检）、发布闸（BLOCK 内容打包面 STOP）。本项目用这三个真实案例展示了同一套方法在不同项目形态下的路由差异：代码项目走 fresh clone 实测支线，设计项目诚实跳过数据与演示段，多知识库项目把凭据挡在包外。

## 现状与限制

本方法已在三个真实项目上完整走通；GitHub 站内实渲染（fence/社交卡）需发布后首查；Skill 本体的可运行包经独立打包链分发。当前版本由项目维护者持续迭代中，欢迎通过 issue 反馈使用中的事实纪律与验收体验。
